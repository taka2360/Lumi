# docs/ を編集するとき

`docs/` は**設計の唯一の正**。コードより先にここが変わる。

## 構成と役割

| ディレクトリ | 役割 | 変更のしやすさ |
|---|---|---|
| `DESIGN.md` | 設計憲法。**全体を理解するのに必要な情報だけ**を置く | 重い |
| `contracts/` | 型と契約。**すべて Confirmed** | **最も重い。ADR 必須** |
| `architecture/` | 各領域の設計 | 中 |
| `interfaces/` | コンポーネント間の契約（型定義） | 中 |
| `decisions/` | ADR。**決定時点の記録** | **追記のみ。書き換えない** |
| `roadmap.md` | Phase・完了条件・未確定事項・リスク | 軽い |

## 書く前に確認すること

1. **[DESIGN.md](../../docs/DESIGN.md) §12 の SSoT 表を見る。** その項目の定義場所は他にないか
2. **表・式・型定義を2箇所目に書かない。** リンクする。要点の1〜2行の再掲は可
3. Confirmed の内容を変えるなら、**先に ADR を書く**
4. 新しい表・式・型を作るなら、**SSoT 表に行が要るか**を確認する

## 書き方

- **日本語**
- **「保証しないこと」を書く。** 誇張した保証を書くと、実装者がそれを前提に他の防御を省く
  - 例: 「Core 侵害でも OS 乗っ取りにならない」とは書かない。B3 が保証するのは権限の上限固定だけ
  - 例: Class B の Tool について「TOCTOU が防止されている」と書かない
- **なぜそうしたかを書く。** 「何を決めたか」だけの文書は、半年後に変更してよいか判断できない
- **反例を書く。** 「これをすると何が壊れるか」が最も効く
- 確定度を明示する: **Confirmed** / Provisional / **Deferred (Phase N)** / 🔴 未決（Phase N 着手前に決める）
- 各ファイルの末尾に**テスト表**を置く。これが実装の受け入れ条件になる

## ADR

`docs/decisions/ADR-NNN-<kebab-case-title>.md`。番号は連番。既存 ADR と同じ構成にする。

Status / Date / 関連 → `## Decision` → `## Reason` → `## Alternatives`（利点も書く）→ `## Trade-offs`（受け入れるコスト / 得るもの）→ `## Consequences`

- **既存の ADR を書き換えない。** 修正が必要なら新しい ADR を書き、古い方の冒頭に「〜が修正した」ブロックを追記する
- ADR 同士の重複は許容する（決定時点の記録なので）

## 編集後

- **内部リンクが壊れていないか確認する**（相対パスの `.md` リンク。ファイル移動・改名の後は必ず）
- DESIGN.md の Revision と「rev.N の変更点」を更新する（大きな変更の場合）
- 影響する他ドキュメントの記述が矛盾していないか確認する

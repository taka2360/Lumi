# 設計とコードの関係

## 設計が先、コードが後

**実装によって設計が変わったら、コードだけを変更しない。**

```
設計変更が必要だと気づく
  → decisions/ に ADR を追加する
  → 該当する docs/ を更新する
  → コードを書く
```

`docs/DESIGN.md` §8 の確定度レベルで扱いが変わる。

| レベル | 変更の扱い |
|---|---|
| **Confirmed** | **ADR を新規作成し、影響範囲を洗ってから変更。** 勝手に変えない |
| Provisional | 通常の設計変更として記録・更新 |
| Deferred | この段階では決めない。決めたくなったら Phase を確認する |

`contracts/` の内容と8つの Invariant は**すべて Confirmed**。ここを変えるときは必ず ADR。

## ADR の書き方

`docs/decisions/ADR-NNN-<kebab-case-title>.md`。既存の ADR-001〜018 と同じ構成にする。

```
Status / Date / 関連（表）
## Decision   何を決めたか。断定形で
## Reason     なぜ。反例・失敗する具体例を書く
## Alternatives  検討した選択肢と、採らなかった理由（利点も書く）
## Trade-offs 受け入れるコスト / 得るもの
## Consequences  この決定の帰結。他のどこが変わるか
```

- **ADR は決定時点の記録。後から書き換えない。** 変更が必要なら新しい ADR を書き、古い方に「〜が修正した」旨を追記する
- 「保証しないこと」を書く。誇張した保証を書くと、実装者がそれを前提に他の防御を省く

## SSoT（単一定義）の規則

**同じ内容を2箇所に書かない。** → 定義場所の一覧は [docs/DESIGN.md](../../docs/DESIGN.md) §12

1. 各項目の**唯一の定義場所**にだけ表・式・型定義を置き、他はリンクする
2. 要点を1〜2行で再掲するのは可。**表や式やコードを再掲しない**
3. **ADR は例外**（決定時点の記録なので重複していても更新しない）
4. 新しい表・式・型を書く前に、DESIGN.md §12 に行が要るかを確認する

## 言語

**ドキュメント・ADR・実装計画・コミットメッセージは日本語。**
コード内の識別子・コメント・docstring は英語で書く（オープンソースとして読まれる前提のため）。
ユーザー向け文言・ログ・エラーメッセージ・アサート失敗メッセージは対象外（日本語のままでよい）。

## やらないこと

- 設計に無い抽象層を「将来使うかもしれない」で足さない（設計原則7）
- Core を過剰に plugin 化しない。**交換したいもの・追加したいものだけ** Extension にする
- Phase を飛ばさない。[roadmap.md](../../docs/roadmap.md) の 🔴（着手前に決めること）が未決なら先にそれを片付ける

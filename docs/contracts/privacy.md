## 解決したい問題

**Lumi は常時マイクを開き、前面アプリを継続観測し、全操作を監査ログに残す。**
そして **Phase 2 から、会話の生ログを永続化する。**

| | 現在（Phase 1 まで） | Phase 2 から |
|---|---|---|
| 会話 | **セッション内メモリのみ。ディスクに残らない** | **Episode として永続化する** |
| Kernel の事実（DomainEvent） | 永続化している。**発話本文は入れていない** | 変わらない |
| 監査ログ | 永続化している | 変わらない |

**このファイルは Phase 2 以降の状態を定義する。** 会話を永続化するのは機能として必要である
（記憶しないキャラクターは Lumi ではない）。しかし、それを**ユーザーが把握できないまま何年も
貯め続ける**なら、それは記憶ではなく蓄積事故である。**永続化を始める前に、ここを決めておく。**

このファイルが答える問いは4つ。

1. **何が**ディスクに残るのか
2. それは**どう守られる**のか。そして**何からは守られない**のか
3. **いつ消える**のか
4. ユーザーが「**全部消して**」と言ったとき、消えるものは何か

## 1. 保存先

**Windows: `%LOCALAPPDATA%\Lumi\`。**

| なぜ | |
|---|---|
| インストール先に置かない | アンインストールで消える場所にユーザーのデータを置かない |
| `%APPDATA%`（ローミング）に置かない | 記憶 DB はドメイン環境でサーバに同期されてよいものではない |

**1ユーザー1データ。** OS のユーザーが分かれていれば、記憶も鍵も分かれる。

## 3. 暗号化

### する

**会話由来のデータを含む DB は、保存時に暗号化する。**

```text
Lumi がランダムな DB 鍵を生成（32 バイト）
  → OS の秘密保管に預ける（Windows: DPAPI / current user スコープ）
  → 起動時に取り出して DB を開く
```

実装は APSW + SQLite3 Multiple Ciphers（`chacha20`）→ [ADR-040](../decisions/ADR-040-encrypted-sqlite-driver.md)。
**保護された blob 自体はファイルである**（上の表の 11 行目）。DPAPI が守るのは中身であって置き場所ではない。

**ユーザーはパスワードを作らないし、管理しない。** 鍵の存在を意識させない。

### 守らないもの

> **保存時の暗号化は「保存されたデータ」を守るのであって、
> 同じユーザー権限で既に実行されているソフトウェアからは守らない。**

DPAPI の鍵は current user スコープであり、**同じユーザーとして動くプロセスは同じように鍵を開ける。**
これは緩和ではなく、この方式の定義そのものである。**防げると書かない。**

| 守れる | 守れない |
|---|---|
| ディスクを直接読まれる | 同一ユーザー権限で動くマルウェア |
| DB ファイルだけを持ち出される | OS 管理者権限を持つ別プロセス |
| バックアップソフト / クラウド同期に載る | ユーザー自身がエクスポートしたファイル |
| 修理・売却した PC のディスクが読まれる | |

**脅威モデルの書き方は [security-boundaries.md](security-boundaries.md) と同じ規則に従う**——
その境界が保証しないことを必ず書く。

### 鍵を失ったら復旧できない

これは事故ではなく**設計上の帰結**である。帰結として2つ:

1. **暗号化された DB ファイルのコピーを「バックアップ」と呼ばない。** 別マシンでは開けない
2. ユーザーに提供するのは**エクスポート**である。
   **エクスポートしたファイルは平文になる。その事実を出力時に明示する**

## 4. 保持期間

**既定は期限あり。設定で延長・無期限を選べる。**

数値は §2 の表が持つ（Episode 90 日 / 監査ログ 180 日 / DomainEvent 30 日 / ログ 7 日）。

### 「忘れる」と「消える」を混ぜない

| | 対象 | 仕組み | 元に戻せるか |
|---|---|---|---|
| **忘れる** | 記憶レコード | salience の減衰 → `archived_at`（[../architecture/memory.md](../architecture/memory.md) §5） | **戻せる**（強い手がかりがあれば思い出す余地を残す） |
| **消える** | Episode / DomainEvent / 監査ログ / 構造化ログ | 保持期間の経過 | 戻せない |

**記憶レコードは保持期間の対象ではない。** 「Factorio が好き」を 90 日で消すのは忘却ではなく破壊である。
**元ログが消えても記憶は残る。**

### なぜ既定で期限を置くのか

「無期限・ユーザーが消すまで消えない」は一見すると誠実だが、**実際には誰も消さない。**
3年後に 10 GB の会話ログがあり、その中身をユーザーが把握していない状態は、
「勝手に消さない」の名のもとに作られた事故である。

**無期限を選べる**ことは重要である。ただしそれは、**ユーザーが自分で選んだ**という形で成立させる。

## 5. 消去

### 「全部消して」

**単一の操作で、§2 の表の「全部消す」列が ✓ の行をすべて消す。** 消去対象は表が定義する。

- 記憶 UI（[../architecture/memory.md](../architecture/memory.md) §8）と同じ画面から到達できる
- 実行前に、**何が消えるかを一覧で見せる**（表の行そのもの）
- 監査ログも対象に含める（下記）

#### 監査ログを消せることと、append-only であることの両立

**この2つは矛盾して見える。** [authority-matrix.md](authority-matrix.md) の静的検査 9 は
「`audit_log` への `DELETE` / `UPDATE` がコードベースに存在しない」であり、
[security-boundaries.md](security-boundaries.md) の append-only は
「**Lumi の全 Tool 経路から**改竄・削除できない」という意味である。

**境界はここに引く。**

| 主体 | 監査ログを消せるか |
|---|---|
| **Tool**（`ToolRegistry.invoke` を通る操作） | **✗ 到達不能。**`fs` の deny パス・専用コネクション・DDL 権限の分離で塞ぐ |
| **LLM の判断・自律行動・Extension** | **✗**（Tool 経路しか持たないため） |
| **保持期間ジョブ / 全消去**（Core の専用サービス） | **✓ ここだけが例外** |

**したがって静的検査 9 は「`audit_log` への `DELETE` / `UPDATE` が、
保持期間ジョブと全消去サービス以外に存在しない」に読み替える。**
例外を2箇所に固定し、そこ以外からは到達できないことを検査する。

> **実装〔2026-08-22 / Phase 2c〕: ユーザーデータを消す `DELETE` は `core/lumi/storage/retention.py`
> にしか無い。** 全消去（Phase 2g）も同じファイルに置く。監査ログを書く
> `storage/audit.py` には削除経路が無く、DB もファイルごと分かれている（`audit.db`）ため、
> **Tool 側の deny パスで名指しできる**。

**「Lumi 自身が消せない」ことと「ユーザーが消せる」ことは別である。**
前者は Invariant（Lumi が自分の足跡を消せない）で、後者はユーザーの権利である。
append-only が守るのは前者であり、**後者まで禁じると「消したくても消せないログ」になる。**

#### 削除の記録は残る

全消去と保持期間の削除は、**「いつ・何件・どの対象を消したか」を新しいレコードとして残す。**
これは監査ログの削除で消えたものの代わりではなく、**削除という操作そのものの記録**である。

| | |
|---|---|
| 残す内容 | 時刻 / 対象（§2 の表の行）/ 件数 / 契機（ユーザー操作 or 保持期間） |
| **残さない内容** | **消したデータの中身。** ダイジェストも残さない（残せば全消去にならない） |
| 保持期間 | **期限なし。**「全部消して」の対象にも**しない**（消した記録まで消えると、消えたことが分からなくなる） |

### 個別の削除

記憶 UI から、記憶レコード単位で物理削除できる。**物理削除はユーザーの明示操作でのみ**である
（[../architecture/memory.md](../architecture/memory.md) §5）。

### アンインストール時

**既定でデータを残す。** アンインストーラが「Lumi が覚えたことも削除する」を
**明示的に、既定オフで**提示する。

> **黙って消さないし、黙って残さない。**

## 6. 音声と、第三者

### 生の音声波形は永続化しない

- マイク入力はリングバッファのみ。**ディスクに書かない**
- **デバッグ用の録音経路も作らない。** 「開発時だけ」の抜け道は、そのまま出荷される
- 永続化されるのは STT 済みのテキストである

### 第三者の発話は残りうる

話者識別は実装しない（Phase 1〜9 のスコープ外。[provenance.md](provenance.md)）。したがって:

- 部屋の中の他人の発話
- スピーカーから流れた音声（YouTube 等。EchoGuard が棄却するのは **Lumi 自身の発話**だけ）

これらが STT され、Episode に残ることは**起こりうる。この限界を隠さない。**

### 帰結として Phase 2 の要件になるもの

| 要件 | なぜ |
|---|---|
| **マイクが開いていることが常に画面上で分かる** | 「聞かれていると思っていなかった」を起こさない |
| **即座にミュートできる** | 気づいた時点で止められなければ、表示に意味がない |
| Episode の閲覧・削除 | 残ってしまったものを消せる（§5） |

## 7. この方針が守られているかの検証

| 検証 | 方法 |
|---|---|
| 表に無い永続化先が増えていないか | 書き込み先ディレクトリの静的検査（[authority-matrix.md](authority-matrix.md) の検査項目に追加） |
| 発話本文が DomainEvent の payload に入っていないか | イベント payload のスキーマ検査 |
| 生波形がディスクに書かれていないか | 音声バッファを扱うモジュールにファイル書き込み経路が無いことの静的検査 |
| 「全部消して」が表の全行に到達するか | 統合テスト（各行に1件ずつ書いてから実行し、残存ゼロを確認する） |
| 保持期間の削除が動くか | 時刻を注入するテスト（**LLM を呼ばずにテストできること**） |

## 決着 — 暗号化の実装〔2026-08-22 / Phase 2a〕

**暗号化 DB と sqlite-vec 拡張・FTS5・PyInstaller の組み合わせは、spike で確認済みである。**
**4項目すべて通った** → [../measurements/phase2.md](../measurements/phase2.md) / 決定は [ADR-040](../decisions/ADR-040-encrypted-sqlite-driver.md)。

| 確認したこと | 結果 |
|---|---|
| 暗号化ビルドで sqlite-vec がロードでき、FTS5 が引けるか | **通る** |
| Windows の wheel があるか | **ある**（`apsw-sqlite3mc` cp312 win_amd64） |
| PyInstaller の配布物に載るか。サイズ増 | **載る。+2.73 MiB** |
| 既存の平文イベント DB からの移行経路 | **移行対象が存在しない**（Phase 1 のイベント DB はインメモリ）。手順は確認済み |

したがって **[ADR-038](../decisions/ADR-038-privacy-and-data-retention.md) は修正しない。**

実装上の帰結:

- 標準ライブラリの `sqlite3` では暗号化 DB を開けないため、**Core の SQLite ドライバは APSW に替わった**
- **オンディスクの DB は鍵なしでは開けない**（`Database.open` が拒否する）。平文で開く引数は無い
- `lumi-core.exe --self-check` が「**この配布物で暗号化が効いているか**」を毎回答える

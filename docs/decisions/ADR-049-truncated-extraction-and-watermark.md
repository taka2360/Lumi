# ADR-049: 抽出に出力上限を入れ、打ち切られた抽出は「バッチを縮めて引き直す」

| | |
|---|---|
| Status | Accepted |
| Date | 2026-09-04 |
| 関連 | [ADR-048](ADR-048-sampling-profiles.md)（この決定を保留した）, [ADR-018](ADR-018-foreground-and-jobs.md), [../architecture/memory.md](../architecture/memory.md) §4, [../interfaces/provider.md](../interfaces/provider.md), [../measurements/phase2.md](../measurements/phase2.md) |
| 実装 | `core/lumi/memory/reflection.py`, `core/lumi/providers/llm/sampling.py` |

## Decision

**抽出（`Purpose.EXTRACTION`）に出力トークン上限を入れる。`EXTRACTION_MAX_TOKENS = 1536`。**

そのうえで、**生成の終わり方ごとに watermark をどうするかを決める。**
表の単一定義は [../architecture/memory.md](../architecture/memory.md) §4 に置く。ここには決定の骨子だけを書く。

1. **打ち切られた答えは捨てる。** `Finish(reason="length")` は結果を破棄する。
   **「パースできたか」では判定しない**——切れた JSON 配列は短い配列として素直にパースされるので、
   打ち切りは**終了理由でしか分からない**
2. ★ **`length` は「次回やり直す」で終わらせず、その場でバッチを半分に縮めて引き直す。**
   抽出は次のパスでも同じ Episode を読むので、**入力だけで決まる打ち切りはその入力に対して毎回再発する**
3. **1発話まで縮めてもなお `length` なら、同じバッチで有限回（`FLOOR_TRUNCATION_RETRIES = 2`）
   引き直してから諦め、watermark を進める。** 諦めたことは `rejected` と error ログに残す
4. ★ **未知の `Finish.reason` と、`Finish` が来ずに終わったストリームは fail-closed。**
   結果を捨て、**watermark を動かさない**
5. **どの試行を始める前にも、その都度 revoke を確認する。** 縮めた再試行も、同じバッチでの
   再サンプルも、等しく「2回目の背景生成」である（[ADR-018](ADR-018-foreground-and-jobs.md)）
6. **revoke は打ち切りに勝つ。** 再サンプル中に revoke されたら、「上限まで `length` だったから諦める」
   という判定も含めて何も決めず、watermark を動かさない
7. ★ **読み残した Episode があるパスは、そこで終わる。** 次の（新しい）Episode に進まない。
   **読む順序がそのまま信念の優先順位だからである**——`unreflected()` は古い順、
   `contradiction.resolve()` は同強度なら後着を勝たせる。古い Episode を半分読んで
   新しいほうに進むと、**古い信念が新しい信念を supersede する**

`EXTRACTION_MAX_TOKENS` は**実測ではなく導出である。**
`CANDIDATE_LIMIT = 8` がパーサ側の受け入れ上限であり、それを超えた分は読まれずに捨てられる。
日本語の `content` を持つ要素1件は圧縮 JSON でおよそ 90〜100 トークンなので、
**パーサが受け取りうる最大の答えが約 850 トークン**になる。1536 はその 1.8 倍であり、
**正常な抽出では発火せず、止まらないモデルは止める**位置に置いた。

## Reason

**上限が無い抽出には保険が無い。** 会話の `max_tokens = 512` は「停止しなくなったモデル」に対する
保険であり、抽出だけがそれを持っていなかった。抽出は `inference_lease` を持つので
foreground が推論を要求すれば revoke されるが、**ユーザーが黙っている限り revoke は来ない**——
つまり暴走した抽出を止めるものが何も無い。アイドル時間と VRAM を無限に焼く。
これが ADR-048 が「上限が無いままである」と Trade-offs に書いた借りである。

**しかし上限を入れると、上限そのものが新しい失敗様式になる。** ADR-048 がこの決定を
保留したのはそのためで、理由は今も正しい。

```
バッチ B が max_tokens を超える答えを生む
  → 打ち切り → 結果を捨てる → watermark を動かさない
  → 次のパスが同じ B を読む → 同じ上限で同じ場所で切れる
  → 永久
```

**しかも詰まるのはその Episode だけではない。** `unreflected()` は古い順に返すので、
**その後ろの Episode 全部が同じ場所で止まる。** アイドルのたびに同じ推論を焼き、
記憶は一件も増えず、画面には何も出ない。
「次回やり直す」は revoke と engine 障害には正しい答えだが、**打ち切りには間違った答えである。**
両者の違いは一点だけ——**要求そのものが大きすぎたのか、要求は妥当で外側が壊れたのか**。
前者は同じ要求を繰り返しても永久に直らず、後者は同じ要求を繰り返せば直る。

**だから「その場で要求を小さくする」が答えになる。** バッチを半分にすれば出力も減り、
読めた分だけ watermark が進む。読まなかった残りは次のパスが読む——**縮めることで失うものは無い。**

**1発話まで縮めた先には、もう縮める余地が無い。** ここで即座に諦めないのは、
抽出が `temperature 0.2` かつ **seed 無し**（製品経路では設定しない）で走る確率的な生成だからである。
1回の `length` は「この発話は抽出不能」の証拠ではなく**引きの悪さでありうる**。
コイン投げ1回で記憶を1件捨てるのは割に合わない。逆に、上限まで全部 `length` なら
それは引きではなく壁であり、**その1発話を諦めて先に進む。**
**1発話ぶんの取りこぼしは損失だが、二度と流れない抽出キューは機能の停止である。**

★ **未知の `Finish.reason` を「詰まる」側に倒すのは、静かな損失より騒がしい停止を選ぶという判断である。**
誰も読んだことのない理由は「答えが完全である」とは仮定できず、
**サーバ側で打ち切られた場合と区別もできない。** ここで watermark を動かすと、
不完全な答えから作った記憶を信じたうえで、**元の転写を二度と読み返さない**——静かで取り返しがつかない。
停止のほうは見える（記憶ウィンドウが `unreflected_turns()` を出す）し、error ログにも出る。
`.claude/rules/python-core.md` の「迷ったら fail-closed」がそのまま当てはまる。

**この fail-closed があるので、Provider 側の `done_reason: null` の正規化が
安全に関わるものになった**（`str(None)` が `"None"` になっていた。PR #49 で修正済み）。
JSON の null ひとつで抽出キューが止まってよいはずがない。

★ **縮小は「読む順序」という既存の保証に触る。** これはレビューで指摘されて気づいた。
`unreflected()` が `ORDER BY started_at` で古い順に返すのは偶然ではなく、
`contradiction.resolve()` が `assertion_mode` だけを見て**同強度なら後着を勝たせる**からである。
`valid_from` は見ていない。**つまり「いつ言われたか」ではなく「いつ書き込まれたか」で勝敗が決まる。**
古い Episode を半分読んで新しい Episode に進むと、この2つの噛み合わせが外れる。

```
E1（月曜・4発話）を length で 2発話に縮めて読む → watermark を 2 に進める
  → 同じパスで E2（火曜）を読む → 火曜の信念が書かれる
  → 次のパスが E1 の残り 2発話を読む → 月曜の信念が書かれ、火曜のを supersede する
```

**古い事実が新しい事実を静かに消す。** これは `UTTERANCE_LIMIT` を超える長さの Episode で
既に起こりうる問題でもあり、縮小はその窓を広げるだけである。
順序を守る最も安いやり方が「読み残したらそのパスを終える」で、
失うのはアイドル1回分の待ち時間であって記憶ではない。

**revoke の確認を `_ask` の直前に置くのは、再試行という経路が新しくできたからである。**
`OllamaProvider.stream()` は `/api/chat` を投げてからトークンを見る。
確認がパスの入口だけだと、**半分に縮めた2回目の生成が revoke 後にユーザーのターンと競合する**——
revoke が防ぐために存在するそのものである。

## Alternatives

| 選択肢 | 利点 | 採らなかった理由 |
|---|---|---|
| **上限を入れない**（現状維持） | この ADR が要らない。打ち切りが起きないので詰まらない | **暴走した抽出を止めるものが無い。** revoke はユーザーが喋るまで来ない |
| 打ち切られた答えをそのまま使う | 実装が要らない | **切れた JSON 配列はパースできてしまう。** 半分の答えを完全な答えとして信じ、watermark を進めて元の転写を捨てる |
| `length` も「次回やり直す」だけにする | 規則が1つで済む | **入力が同じなら次回も同じ場所で切れる。** その Episode 以降が永久に詰まる（本文の図） |
| 縮めずに、同じバッチを何度も引き直す | 発話を捨てずに済む | 大きすぎる要求は**引き直しでは小さくならない。** 詰まりを推論で焼くだけ |
| 1発話で `length` なら即座に諦める | 単純で、必ず終わる | **抽出は seed 無しの確率的生成である。** 1回の `length` は引きの悪さでありうる。コイン投げで記憶を捨てる |
| 諦めず、その Episode を永久に retry する | 記憶を1件も捨てない | **止まったキューは機能の停止である。** 捨てるのは1発話、詰まらせるのは全 Episode |
| 未知の `Finish.reason` を `stop` として扱う | 詰まらない | **不完全な答えを信じて転写を捨てる。** 静かで取り返しがつかない。fail-closed の逆 |
| **プロンプトで件数上限を伝える**（"Extract at most 8"） | 打ち切りの主因（モデルが 20 件書こうとする）を**入口で断てる**可能性がある。バッチ縮小より根本的 | **プロンプトは実機で2回壊れている**（[../measurements/phase2.md](../measurements/phase2.md)）。`[]` しか返さなくなった件も subject が潰れた件も、机上では出なかった。**実測なしに触らない。** これは上限機構と排他ではないので、測れる場所ができたら別途足せる |
| バッチを 1 ずつ減らす | 取りこぼす発話が最小になる | 40 → 1 が最悪 39 世代になる。**半分なら 6 世代で床に着く** |

## Trade-offs

**受け入れるコスト。**

- **1発話を諦めうる。** 上限まで `length` を返し続けた発話は抽出されないまま watermark を越える。
  損失は `rejected` と error ログに残るが、**記憶にはならない**
- **最悪の1 Episode が 8 世代を使う**（40→20→10→5→2→1 の 6 回で床に着き、床で 2 回引き直す）。
  アイドル時にしか走らず、各世代は `max_tokens` で頭を押さえられ、どの試行の直前でも revoke で捨てられる
- **`EXTRACTION_MAX_TOKENS = 1536` は導出であって実測ではない。** 抽出の出力トークン数は測っていない。
  `CANDIDATE_LIMIT` から引いた上界の 1.8 倍という根拠しか無く、**測ったら変わりうる**
- **未知の `Finish.reason` は抽出キューを止める。** 新しい Provider や新しい Ollama が
  知らない理由を返し始めたら、記憶が作られなくなる。**それは error ログと記憶ウィンドウに出る**が、
  ユーザーがそれを見るとは限らない
- ★ **隣り合う発話が分断されうる。** 縮小は転写を前半と後半に割り、両者が同じプロンプトに
  同席することは二度と無い。ユーザーの短い返事が Lumi の直前の問いに依存していた場合、
  **どちらの側でも取れない記憶が出る**——1発話も飛ばしていないのに落ちる。
  `UTTERANCE_LIMIT` の境界に元からある性質だが、縮小は境界を会話の途中の任意の位置に作る。
  **オーバーラップを持たせる案は採らなかった**——重ねる幅は測っていない数値であり、
  同じ理由で「プロンプトに件数上限を書く」案も見送っている（Alternatives）。
  そもそも縮小が発火するのは 1536 トークンを超える出力が出たときだけで、
  詰まった Episode を永久に読み返すほうが高くつく
- 読み残しでパスが終わるので、**1回のアイドルで進む Episode が減る。**
  長い Episode が溜まっていると追いつくのに複数回のアイドルが要る
- 状態が増える。`_Ask` という「答えの終わり方」の分類が、`ReflectionReport.interrupted` とは
  別に必要になった。**2つが言っていることは違う**——`interrupted` は「このパスはここで止まり
  watermark は据え置き」、`_Ask` は「その理由なので次に何を試してよいか」

**得るもの。**

- **抽出キューが止まらない。** どの入力に対しても、有限回で「進む」か「明示的に諦める」に着く
- **暴走した抽出が止まる。** 会話が持っていた保険を抽出も持つ
- **黙って劣化しない。** 捨てた発話は `rejected` に、止めた理由は error ログに出る
- 打ち切りが**パースの偶然に依存しなくなる。** 終了理由を読むので、切れた配列を短い配列と
  取り違えることがない

## Consequences

- `Purpose.EXTRACTION` の `max_tokens` が `None` から 1536 になる。
  [../interfaces/provider.md](../interfaces/provider.md) の表を更新する（**あの表が単一定義**）
- [../architecture/memory.md](../architecture/memory.md) §4 に
  「生成の終わり方 × watermark」の表が入る。**そこが単一定義**であり、
  `memory/reflection.py` の `_Ask` はそれを実装する
- `ReflectionJob` に `_reflect_episode`（1 Episode ぶんの縮小ループ）が入り、
  `_reflect` は「1プロンプト = 1試行」に狭まる。`_ask` は文字列と**終わり方**を返す
- **抽出の出力トークン数は次に実機を触るときに測る。** 測れたら
  [../measurements/phase2.md](../measurements/phase2.md) に入れ、必要なら上限を引き直す。
  上限の値そのものは ADR ではなく `sampling.py` の定数である
- **プロンプトに件数上限を書く案は残っている。** この決定と排他ではなく、
  実機で A/B が取れる場所ができたら別の変更として検討する

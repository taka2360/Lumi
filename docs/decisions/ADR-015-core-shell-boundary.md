# ADR-015: Core→Shell をセキュリティ境界とし、Shell に拒否権のみを持たせる

| | |
|---|---|
| Status | Accepted |
| Date | 2026-08-14 |
| 関連 | [../contracts/security-boundaries.md](../contracts/security-boundaries.md), [../contracts/invariants.md](../contracts/invariants.md), [../interfaces/shell.md](../interfaces/shell.md) |

---

## Decision

**Core → Shell（B3）を明示的なセキュリティ境界とする。** Shell は Core を信頼しない。

Shell は `os.*` に対して以下を適用する（**Core の指示内容にかかわらず**）。

1. WS token による認証
2. `os.*` コマンドの allowlist
3. schema validation
4. **保護対象ウィンドウへの `os.input.*` / `os.capture.*` の無条件拒否**（Invariant 8）

**Shell に置くのは「拒否」だけであり「許可」は絶対に置かない。**

### B3 が保証すること — 「権限の上限固定」

> Core が侵害された場合、攻撃者は Core に付与されている OS capability を行使できる。
> B3 が保証するのは次の3点のみ。
>
> 1. allowlist 外の OS 操作ができない
> 2. 保護対象ウィンドウへの入力・キャプチャができない
> 3. **権限昇格が自己承認によって行われない**
>
> **被害の完全な防止ではなく、権限の上限固定である。**
> 本質は「**侵害された Core は、侵害前の Core より強くなれない**」。

---

## Reason

### Shell は実質的に root capability を持っている

| 能力 | 意味 |
|---|---|
| screenshot | 画面録画 |
| input injection | キーボード・マウスの完全制御 |
| window create | 任意のウィンドウ表示 |
| process launch | 任意プロセスの起動 |

**これらを無条件に Core の指示で実行すると、Core が侵害された瞬間に OS 乗っ取りが成立する。**

### 「Shell は判断を持たない」と「無条件に従う」は違う

当初の設計は「Shell は OS 特権プリミティブのみ。判断を持たない」だった。これは**判断の権威**についての記述であり、**検証をしない**という意味ではなかった。

区別を明確にする:

| | Shell が持つか |
|---|---|
| 「この操作をすべきか」の判断 | **持たない**（Core が決める） |
| 「この要求は形式的に妥当か」の検証 | **持つ** |
| 「この対象は絶対に触ってはいけない」の拒否 | **持つ**（Invariant 8） |

### Invariant 8 が Core の外にある理由

**この判断が守るべき相手が Core 自身だから。**

Core の中に置いたら、Core が侵害された時点で無意味になる。

```
攻撃者が Core を侵害
  → 「権限プロンプトの Allow ボタンをクリックしろ」と Shell に指示
  → Shell が無条件に従う
  → 攻撃者が自分で自分に権限を与える
```

**Shell が拒否することで、この経路が塞がれる。**

### 拒否権は権威の分散にならない

Invariant 1（判断は Core だけ）の唯一の例外だが、これは権威の分散ではない。

**拒否権は安全側にしか倒れない。** Shell が拒否を間違えても「できるはずのことができない」だけで、「できてはいけないことができる」にはならない。

**許可を Shell に置いたら話が違う。** それは権威の分散であり、Invariant 1 の実質的な破壊になる。だから絶対に置かない。

---

## Alternatives

### A. Shell は Core を完全に信頼する（当初案）

**利点:** 実装が単純。Shell が薄くなる
**欠点:** **Core の侵害 = OS 乗っ取り。** かつ Core が「Allow をクリックしろ」と言えば権限昇格が自動化される

### B. Invariant 8 を Core 側だけに実装する

**利点:** 判断が Core に一元化される（Invariant 1 が純粋に保たれる）
**欠点:** **Core が侵害されたら無意味。** 守るべき相手が Core なのに、Core に守らせている

### C. Shell に完全な Policy を持たせる

**利点:** 多層防御が最も厚い
**欠点:** Policy が2箇所になり、**齟齬が生じる**。どちらが正なのかが曖昧になる。Invariant 1 の実質的な破壊

### D. Shell と Core を同一プロセスにする

**利点:** 境界が無くなるので問題も無くなる
**欠点:** 境界が無いということは、**Core の侵害が直接 OS 特権になる**。問題が消えたのではなく、防御が消えている

---

## Trade-offs

### 受け入れるコスト

| コスト | 内容 |
|---|---|
| Shell 側にハードコードが入る | 保護対象の判定ロジック。設定で変えられない |
| 二重実装 | Core 側の `BindVerifier` と Shell 側の拒否 |
| allowlist のメンテナンス | `os.*` を増やすたびに allowlist も更新する |
| 過剰な拒否のリスク | 正当な操作が拒否されうる |

### 二重実装は意図的

| 層 | 実装 |
|---|---|
| Core | `input` lane の `BindVerifier` が、bind した HWND が保護対象でないことを検証 |
| Shell | 対象ウィンドウが保護対象なら無条件拒否。**Core の指示内容を見ない** |

**片方の実装ミスで穴が空かないようにするため。** これは冗長ではなく多層防御である。

---

## Consequences

### 保証しないことを明記する

**「Core 侵害でも OS 乗っ取りにならない」とは書かない。** 誇張した保証を書くと、実装者がそれを前提に他の防御を省く。

保証しないこと:
- Core が既に持っている capability の悪用（スクリーンショットの窃取、許可済みパスの読み取り等）
- OS 管理者権限を持つ別プロセスからの攻撃
- Shell 自体が侵害された場合

### 権限プロンプトを独立ウィンドウにする

保護対象を明確にするため、権限プロンプトは Stage 内のモーダルではなく**独立したウィンドウ**にする。

これによりウィンドウハンドルで判定でき、Shell 側の実装が単純になる。

### 保護対象の一覧（ハードコード）

- 権限プロンプトウィンドウ
- Lumi 自身のメインウィンドウ・設定ウィンドウ

Core 側の Policy では加えて:
- Lumi のプロセス・設定ファイル・監査ログ

### Phase 0 で骨格を作る

Phase 0 の完了条件に含める。

> **未知の `os.*` コマンドを Shell に送ると拒否され、ログに残る**

本格的な allowlist と保護対象判定は Phase 4 だが、**検証層の存在自体は Phase 0 で作る**。後から挟み込むと全 `os.*` 呼び出しの経路が変わるため。

### AIRI から借りた発想

AIRI の `computer-use-mcp` の README に「**AIRI 自身がデフォルト deny リストに入っている**（自己操作の防止）」とある。

**これは正しい設計である。** Lumi はこれを Invariant 8 として一般化し、Shell 側にハードコードすることで、Core の侵害に対しても有効にする。

### この判断を見直す条件

- Shell 側の拒否が正当な操作を妨げるケースが頻発する
- 保護対象の判定が Windows のウィンドウ管理の変更で壊れる

**その場合も「拒否を緩める」のではなく「保護対象の判定を正確にする」方向で対処する。** 拒否権を弱めることは、この ADR の目的そのものを失わせる。

# ADR-025: TTS に GPU を使えるようにする

| | |
|---|---|
| Status | Accepted |
| Date | 2026-08-16 |
| 修正する ADR | [ADR-008](ADR-008-provider-abstraction.md)（「TTS は別プロセス・CPU で VRAM を一切消費しない」） |
| 関連 | [DESIGN.md](../DESIGN.md) §7, [architecture/audio.md](../architecture/audio.md) §6-7, [measurements/phase1.md](../measurements/phase1.md) |

## Decision

**TTS エンジンは GPU を使ってよい。**

| | |
|---|---|
| 既定 | **CUDA デバイスがあれば使う。無ければ CPU** |
| 設定 | **CPU を強制できる**（VRAM が逼迫する環境のため） |
| 可視性 | **どちらで動いているかを状態として出す。** 黙って落とさない |

ADR-008 の「**VRAM を一切消費しない**」という性質を、TTS の選定理由から外す。
AivisSpeech / VOICEVOX を選んだ他の理由（日本語品質・別プロセス・ライセンス境界）は変わらない。

## Reason

**ADR-008 は「TTS を GPU に載せるといくら掛かり、いくら速くなるか」を測らずに書かれていた。**
Phase 1 で測ったところ、前提が2つとも外れていた。

### 1. CPU の TTS は「軽い」どころか、24 コアを飽和させる

〔2026-08-16 実測。RTX 4070 12GB / 24 論理コア / AivisSpeech Engine 1.2.0〕

| | 実測 |
|---|---|
| 1リクエストの実時間 | 836 ms |
| 1リクエストの **CPU 時間** | **19.3 秒** |
| 並列度 | **23.1x**（= 全コアを使い切っている） |
| 4並列のスループット | 3.28 秒（逐次 3.35 秒）＝ **改善しない** |

**スレッド数を増やす余地はゼロ。** `--cpu_num_threads` は AivisSpeech には存在しない
（VOICEVOX にはある）が、あっても意味がない。

「CPU だから他の処理と共存できる」という暗黙の前提も成り立たない。
**発話のたびに全コアが 0.8 秒間占有される。**

### 2. GPU に載せると 2 倍速く、コストは 1.0 GB

| 配置 | `tts_first_audio_ms` p50 | VRAM |
|---|---|---|
| CPU | 約 900 ms | 0 |
| **GPU** | **約 440 ms** | **+1.0 GB** |

合成時間が**テキスト長にほぼ依存しなくなる**（CPU: 3文字 863 ms → 17文字 1230 ms /
GPU: 3〜17文字とも約 340 ms）のも大きい。**遅延が予測可能になる。**

### 3. これが無いと Phase 1 の完了条件に届かない

完了条件は **p95 2.0 秒**。区間予算（[audio.md](../architecture/audio.md) §7）の
「第1文 TTS 生成 0.20 s」に対し、CPU の実測は 0.9 秒で **4.5 倍**。
他の区間をすべて予算内に収めても届かない。

**VRAM の総量は問題にならない。** 実測 LLM 5.5 GB + TTS 1.0 GB + STT 0.4 GB = **6.9 / 12 GB**。
「LLM に全振り」が守ろうとしていた余裕は、そもそも使われていなかった。

## Alternatives

### A. CPU のまま、SLO を実測に合わせて緩める

**利点**: ADR-008 をそのまま保てる。VRAM の小さい GPU でも同じ体験になる。
**採らない理由**: p95 2.0 秒は Lumi の中核的な約束（DESIGN.md §1「話しかければ答える」）であって、
実装の都合で下げるものではない。**測ったら遅かったので目標を下げる、は順序が逆。**

### B. 第1セグメントをさらに短く切る

**利点**: コード変更だけで済む。
**採らない理由**: **効かない。** CPU の合成時間は約 800 ms の固定費に支配されており、
3文字でも 863 ms かかる（§Reason 2）。

### C. より軽い音声モデルに替える

**利点**: VRAM を使わない。
**採らない理由**: 固定費は Style-Bert-VITS2 のアーキテクチャに由来し、モデルの重みの問題ではない。
**そして声質は Content Pack がユーザーに約束するもの**であり、レイテンシのために替えるものではない。

### D. 常に GPU（CPU フォールバックを持たない）

**利点**: 分岐が減る。
**採らない理由**: NVIDIA GPU の無い PC で Lumi が起動しなくなる。
**「喋れないが壊れていない」は正常な状態**という原則（setup.md §1）に反する。

## Trade-offs

### 受け入れるコスト

- **VRAM 1.0 GB を TTS が持つ。** VRAM 6 GB 級の GPU では LLM のサイズを落とす判断が要る
- **構成が2通りになる**（GPU / CPU）。レイテンシが環境で 2 倍変わり、**SLO は GPU 構成での約束になる**
- Phase 5 の `ModelResourceManager` が扱う対象が1つ増える
- **ADR-008 の「VRAM を一切消費しない」という記述が、以後は誤りになる**

### 得るもの

- `tts_first_audio_ms` が 900 ms → 440 ms
- **合成時間がテキスト長にほぼ依存しなくなる**（遅延が予測可能になる）
- 発話のたびに全 CPU コアが 0.8 秒占有される状態が解消する。
  **これは barge-in にとって重要**で、VAD スレッドと再生コールバックが CPU を奪われなくなる

## Consequences

| 変わるもの | 内容 |
|---|---|
| [DESIGN.md](../DESIGN.md) §7 | GPU / VRAM 戦略の表で TTS が「別プロセス・CPU / VRAM 0」ではなくなる |
| [architecture/audio.md](../architecture/audio.md) §7 | SLO は **GPU 構成での約束**であることを明記する |
| [architecture/setup.md](../architecture/setup.md) | どちらで動いているかを状態として出す |
| `EngineProcess` | `--use_gpu` を渡す経路を持つ |
| Phase 5 | `ModelResourceManager` の対象に TTS が入る |

**ADR-008 の他の決定（Provider 抽象・`load`/`unload`/`resource_hint`・最初の3実装）は変わらない。**
覆すのは「TTS が VRAM を消費しない」という一点だけである。

### 保証しないこと

- **GPU なら常に速い、とは言っていない。** 実測は RTX 4070 12GB / LLM が同居した状態での値であり、
  VRAM が逼迫すれば TTS も LLM も遅くなる。**その調停は Phase 5**
- **CPU 構成で SLO を満たすとは言わない。** 満たさないことを実測した上で、
  そういう環境があることを受け入れている

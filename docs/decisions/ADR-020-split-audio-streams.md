# ADR-020: 入出力を別ストリームで開き、reference signal は Core が自前で持つ

| | |
|---|---|
| Status | Accepted |
| Date | 2026-08-15 |
| 関連 | [ADR-003](ADR-003-audio-in-core.md)（本 ADR がその Trade-offs「duplex stream を Phase 1 から開く」を修正する）, [../architecture/audio.md](../architecture/audio.md), [../measurements/phase0.md](../measurements/phase0.md) |

---

## Decision

マイク入力と再生を、**それぞれ独立した PortAudio ストリーム**で開く。**duplex stream は使わない。**

1. **reference signal は、Core が再生リングに書いたサンプルそのもの**とする。ハードウェアの reference channel に依存しない
2. 入出力の整合は、**各コールバックで採る共通の実時間（`time.perf_counter()`）とフレーム番号**で取る。ドリフト補正は Phase 2 で、必要になったときだけ実装する
3. ストリームは**デバイスが受け付けるサンプルレートで開く。** VAD の 16 kHz へは **Core 内でリサンプルする**（「16 kHz で開く」は成立しない）
4. Windows のホスト API は **WASAPI を明示的に選ぶ。** PortAudio の既定に任せない
5. **開通の条件は「最初のフレームが規定時間内に届くこと」。** `open()` の成功では足りない

---

## Reason

Phase 0 で実測した（[../measurements/phase0.md](../measurements/phase0.md) に条件と数値）。**当初の想定は2箇所で外れていた。**

### duplex が開ける条件は「同一デバイスかどうか」ではない

| 組み合わせ | 結果 |
|---|---|
| WASAPI / **別物理デバイス**（USB マイク 48k + HDMI モニタ 48k） | **開ける。** xrun 0 |
| WASAPI / **同一物理デバイス**（USB ヘッドセットのマイク 48k + ヘッドホン 96k） | **開けない**（Invalid sample rate） |
| WASAPI / 16 kHz（VAD のレート） | **開けない**（共有モードは mix format のレートしか受け付けない） |
| ホスト API を跨ぐ（MME 入力 + WASAPI 出力） | **開けない**（Illegal combination of I/O devices。PortAudio が構造的に拒否する） |
| MME / 同一・別物理とも | 開ける。ただし**出力遅延 209 ms** で xrun あり |

条件は「**入出力が同じホスト API で、かつ両者が受け入れる単一のサンプルレートが存在すること**」である。
WASAPI 共有モードでは各エンドポイントの mix format が固定なので、**同一の USB ヘッドセットですら
マイク 48 kHz / ヘッドホン 96 kHz で噛み合わず開けない。**

つまり duplex の可否は**ユーザーの機材が決める**。設計で担保できない。

### 分離ストリームでもドリフトしない

| 測定 | 相対ドリフト |
|---|---|
| USB マイク vs HDMI モニタ（分離、120 s） | -1.5 ppm = 0.09 ms/分 |
| USB マイク vs オンボード Realtek（分離、90 s） | +1.8 ppm = 0.11 ms/分 |
| USB マイク 48k vs 同じヘッドセットの出力 96k（分離、120 s） | +1.4 ppm = 0.08 ms/分 |
| duplex（同一コールバック、120 s） | +3.4 ppm（実時間比。split の入力 +4.1 / 出力 +5.6 と**有意差なし**） |

**これらの値は測定分解能とほぼ同じである。** コールバックの先読み量が 3 ms 程度揺れるため、
120 秒の測定で分離できるのは数 ppm まで。**正しい主張は「1.5 ppm だった」ではなく
「有意なドリフトは観測されなかった」。** 小さい値を根拠に「ドリフトしない」と言ってはいけない。

**duplex に固執する理由が消えた。** 「クロックドリフトで reference がずれて AEC が壊れる」という
当初の懸念（audio.md §2 の 🔴）は、少なくとも Windows / WASAPI 共有モードでは観測されない。

### そもそも reference をハードウェアから取る必要がない

**Lumi は再生する音を自分で作っている。** 何をいつ再生バッファに書いたかを Core は正確に知っており、
これは EchoGuard L3（テキストレベルの自己エコー棄却）が成立するのと同じ根拠である。

ハードウェアの reference channel が与えるのは「実際にスピーカーへ出た信号」だが、
**それが要るのは音量やミキサーの介入まで打ち消したい場合**であり、Phase 2 の AEC は
遅延推定器を自前で持つ（`webrtc-audio-processing` は持っている）。

### 経路は1本であるべき

「duplex を試し、失敗したら分離に落ちる」は経路が2本になる。
**barge-in は Lumi の中核であり、その土台がユーザーの機材によって別物になるのは受け入れられない。**
めったに通らない方の経路が腐り、腐ったことに気づくのは他人の PC の上である。

## Alternatives

### A. duplex を第一選択にし、開けなければ分離へフォールバックする（当初案）

**利点:** 入出力が単一クロックであることが構造的に保証される。reference channel がハードウェアから得られる
**欠点:** 上記のとおり**主要な構成（USB ヘッドセット）で開けない。** 経路が2本になる。しかも実測上、得られる利益（ドリフトの解消）が測定限界以下

### B. MME / DirectSound を使って duplex を確実に開く

**利点:** レートもデバイスの組み合わせも自由。**どんな構成でも開ける**（実測で確認）
**欠点:** **出力遅延 209 ms。** barge-in の mute latency 目標 50 ms に対して桁が違う。xrun も観測された

### C. WASAPI 排他モードで開く

**利点:** 低遅延。任意のサンプルレートをデバイスに直接要求できる（16 kHz で開ける可能性がある）
**欠点:** **他のアプリが音を出せなくなる。** デスクトップに常駐するキャラクターがオーディオデバイスを
独占するのは論外である。**未実測**（この理由で採らないため測っていない）

---

## Trade-offs

### 受け入れるコスト

- **入出力が同一クロックであることが保証されなくなる。** 実測では有意差が出なかったが、これは
  **Windows 共有モードのサンプルレート変換がデバイス間の差を吸収した結果である可能性が高く、他 OS では成り立たない**
- **リサンプラが必須になる**（Phase 1）。デバイス既定のレート → VAD の 16 kHz
- 入出力の整合を自前で持つ必要がある（フレーム番号 + 共通の実時間）

### 得るもの

- **経路が1本。** ユーザーの機材で barge-in の土台が変わらない
- macOS で別デバイスの duplex に集約デバイス（aggregate device）の作成が要る問題を、最初から回避できる
- reference が Core の中にあるので、**デバイスやエンジンが何をしようと、Lumi は自分が何を鳴らしたかを知っている**

### 保証しないこと

- **音響的なエコー経路の遅延が安定することは保証しない。** ここで測ったのは
  **アプリから見たストリームのペース**であり、スピーカーから出てマイクに入るまでの実遅延ではない
- WASAPI 排他モード・Windows 以外の OS・一部の USB オーディオ機器は**未実測**
- 観測されたのは**この1台での「有意差なし」**であって、「ドリフトしない」ことの証明ではない。
  Phase 2 の AEC は、ドリフトが無いことを前提にしてはならない

---

## Consequences

- [../architecture/audio.md](../architecture/audio.md) §2 の構成図から duplex stream が消え、
  capture / playback の2ストリームと reference リングに置き換わる。§2 の 🔴 が解消する
- [../roadmap.md](../roadmap.md) Phase 0 の「duplex stream の骨格」は
  **「デバイス選択と開通確認の骨格 + 実測」**に置き換わる。未確定事項 #4 が解消する
- ADR-003 の Trade-offs「duplex stream を Phase 1 から開く」は**本 ADR が修正する**
- **新しい実装要件が2つ生じる**
  1. **入力デバイスが1つも無い状態**を明示的に扱う（実測したマシンの初期状態がこれだった）
  2. **`open()` に成功してもフレームが1つも来ないデバイスがある**（無効化されたエンドポイント）。
     開通は最初のフレームの到着で判定する
- Phase 2 で AEC を入れるとき、**遅延推定を必ず持つ。** ドリフトが小さいことを設計の前提にしない

### この判断を見直す条件

Phase 2 で AEC が実用水準に達せず、**その原因が入出力のクロック差だと切り分けられた**場合。
その場合でも戻り先は duplex ではなく、**参照信号の再サンプリング**である（duplex は機材依存で開けないため）。

# ADR-047: 左ボタンをキャラクターとのインタラクションに予約し、アプリ操作は右クリックへ移す

| | |
|---|---|
| Status | Accepted |
| Date | 2026-08-30 |
| 関連 | [architecture/ui.md](../architecture/ui.md) §1「アプリ操作は `stage` ウィンドウからも到達できる」/ §2「ウィンドウの移動と大きさ」、[ADR-042](ADR-042-panel-windows-and-panel-role.md) |

## Decision

`stage` ウィンドウのキャラクター表面で、ポインタ操作を次のように割り当てる。

| 操作 | 割り当て |
|---|---|
| 左クリック / 左ドラッグ | **キャラクターとのインタラクション用に予約する。アプリ操作を載せない**〔中身は Phase 未定〕 |
| ホイール | 表示サイズの変更（従来どおり `shell.window.scale`） |
| `alt` + 左ドラッグ / 中ドラッグ | ウィンドウの移動（`shell.window.drag.start`） |
| 右クリック | アプリ操作パレットの表示 |

**ホバーだけではアプリ操作を表示しない。** 従来はカーソルを載せると操作列が出ていたが、これをやめる。

**パレットは OS のコンテキストメニューではなく、`stage` ウィンドウ内の小さなフローティング要素**とする。
中身は既存の `AppActions`（⚙ 設定 / ◎ インスペクター / ✿ 記憶 / ⓘ クレジット / ⏻ 終了）をそのまま使う。

**この割り当ては `stage` ウィンドウが出しているものすべてに適用する。** キャラクターが
まだ出せない `setup` / `installing` / `starting` / `blocked` のローディング・セットアップ画面も同じ。
**あの画面はキャラクターの代役であって、ダイアログではない。**

**右クリックが見えない操作である代償を、静的な `help` ウィンドウで払う。**
トレイメニューの先頭と操作パレットの両方から開ける、Core に繋がらない1画面。

## Reason

**Lumi は「ウィンドウ上のチャットボット」ではなく、デスクトップに住んでいるものとして見せる。**
ホバーで設定ボタンが生えてくるのは、そこにアプリがあると宣言する動きである。カーソルを
通り過ぎさせただけで管理 UI が現れると、キャラクターは「操作対象のウィジェット」に見える。

左ボタンを移動に使っているのが具体的な障害になる。**撫でる・触る・クリックで反応する**は
すべて左ボタンの操作であり、これを後から入れようとすると、左ドラッグはウィンドウ移動と
撫でるの両方を意味することになる。**どちらに解釈するかを毎回推測する設計にはできない**
（押した瞬間に `start_dragging` を呼ぶ現在の実装では、そもそも後から分岐できない）。
移動を修飾キーと中ボタンへ退避させれば、左ボタンは丸ごと空く。

**OS のコンテキストメニューを使わない理由**は大きさである。Windows 標準のメニューは
キャラクターより大きく、348×522 のウィンドウの上に出すと**キャラクターが完全に隠れる**。
既にアイコン列という小さな表現を持っているので、それを浮かせるだけでよい。

**ローディング画面だけ違う操作にはできない。** 同じウィンドウで、同じ場所に出ていて、
入れ替わるだけのものである。ホバーで操作列が出るかどうか、素の左ドラッグで動くかどうかが
**Lumi がその時たまたま何をしているかで変わる**なら、それは誰にも覚えられない。
セットアップ画面が左ドラッグで動かせなくなるのは実際の劣化だが、[終了] も
[Ollama を開く] も**カード自身が持っている**（ADR-034）ので、行き止まりにはならない。

**見えない操作には、見える説明を用意する。** 右クリックを知らなければ何も開けない、
というのがこの決定の最大の代償である。`help` を**静的なページ**にするのは、
**その説明が最も要る場面が `blocked` の画面だから**——Core が上がっていないときに
読めない操作説明は、操作説明ではない。credits と同じ理由（配布物としての義務）ではなく、
help 自身の理由でこうなっている。トレイの先頭に置くのは、
**パレットに辿り着けない人が持っている経路がトレイしか無いため。**

**「外側クリックで閉じる」はヒット領域を広げないと届かない。** ヒット領域の外は Shell が
クリックスルーにするので、パレットを開いたまま何もしないと、パレット外のクリックは
背後のアプリに行ってしまい Stage には来ない。**開いている間だけヒット領域をウィンドウ全面にする。**
これはメニューが最初のクリックを飲む一般的な挙動と一致し、閉じれば元の領域に戻る。

**フォーカスを失ったときも閉じる。** どの項目も自前のウィンドウを開き、そちらがフォーカスを
取る。閉じないと、戻ってきたときにパレットがキャラクターの上に残っている。失敗したときは
何も開かずフォーカスも移らないので、`AppActions` のエラー表示はそのまま画面に残る。

## Alternatives

**ホバー表示を残したまま右クリックも足す。** 発見しやすさは最良で、既存の利点を失わない。
採らなかったのは、**残すと何も解決しないため**。ホバーで管理 UI が出ること自体が変えたい
挙動であり、両方あるならユーザーが目にするのは常にホバーの方である。

**OS のネイティブメニュー（Tauri の `Menu`）。** OS の作法に一致し、画面端の回り込みも
OS が面倒を見る。採らなかったのは上記の大きさの問題と、**項目のラベルが Shell 側の
文字列になり、i18n が Stage と Shell に二重化する**ため。既存の操作列は `stage/src/i18n` を
通っており、そこへ戻す理由がない。

**起動・セットアップ画面だけ従来どおりにする。** キャラクターに会う前のユーザーが
修飾キー無しでウィンドウを動かせる、という利点は実在する。採らなかったのは、
**同じウィンドウの同じ場所で操作体系が2つになるため**。しかもユーザーから見て
どちらが有効かは、Lumi の内部状態（`boot`）でしか決まらない。

**移動を `ctrl` + 左ドラッグにする。** `alt` を選んだのは、Linux の多くの WM で
「`alt` + ドラッグでウィンドウを動かす」が既に体に入っている操作だからである。
中ドラッグも同時に受けるのは、修飾キーを知らない場合の逃げ道として。

**左ドラッグ移動を単に廃止し、移動はトレイから。** 移動は頻度の高い操作であり、
メニュー経由にするのは明確な劣化である。

## Trade-offs

**受け入れるコスト**

- **右クリックは見えない操作である。** ホバーで出ていたものが、知らなければ辿り着けなくなる。
  `help` とトレイが代替経路になるが、**トレイを知らないユーザーには何も見えない**という
  一段は残る。ここは埋めきれていない
- ウィンドウの移動が修飾キーを要求するようになる。素朴に掴んで動かせない。
  **セットアップ画面でも同じ**で、Lumi に会う前のユーザーにこれを課す
- 静的ページが2つになる（credits と help）。**どちらも i18n を通すので、翻訳の追随先が増える**
- パレット表示中はウィンドウ全面がクリックスルーでなくなる。背後のアプリを触ろうとした
  最初のクリックがパレットを閉じるだけになる

**得るもの**

- 通常時、画面に出ているのはキャラクター（とマイク表示）だけになる
- **操作体系がウィンドウ全体で1つになる。** 起動中・セットアップ中・通常時で
  同じ手が通る
- 左ボタンが丸ごと空く。撫でる・触るを**既存の操作を壊さずに**後から入れられる
- 操作の意味が押したボタンだけで決まる。実行時の推測が要らない

## Consequences

- `docs/architecture/ui.md` §1 の「操作領域はホバー中だけ表示し」という規定を置き換える
- `docs/architecture/ui.md` §2 の移動の行を書き換える。ホイールの行は変わらない
- `PlatformShell` は変わらない。**Shell 側のコマンドも増えない**——右クリックの解釈も
  パレットの配置も Stage 内で完結し、`shell.*` に新しい面は増えない
- **`help` ウィンドウを追加する。** `WindowKind::Help` / `shell_help_open` /
  トレイの先頭。credits と同じ「Core に繋がらない静的ページ」の形をとる
- 操作パレットの項目が6つになる（⚙ ◎ ✿ ? ⓘ ⏻）。**グリフと名前の対応は1箇所**
  （`stage/src/actions/items.ts`）に置き、ボタンと help の両方がそこを読む。
  説明側のグリフがボタンとずれるのは、2箇所に書いた場合に必ず起きる
- **初回ヒントは今回は決めない。** パレットは開く位置（`{x, y}`）だけを状態に持つ形にし、
  後からヒントを足すときに構造を壊さないようにしておく
- `AppActions` を出す場所が**パレット1箇所だけ**になる。`inspect-anchor` は消える
- マイク表示は**この決定の対象外**で、従来どおり常時表示する。部屋が聞かれているかどうかは
  探して見つけるものではない（ui.md §5b）

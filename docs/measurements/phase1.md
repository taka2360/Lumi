## 依存の追加とサイズ（R1 の再判定）

**Step C（Provider 基盤）で 16 パッケージが増えた。** STT のためである。

| パッケージ | site-packages 上のサイズ | 何のため |
|---|---|---|
| ctranslate2 | 59.8 MB | faster-whisper の推論エンジン |
| onnxruntime | 38.6 MB | Silero VAD（Phase 1 Step D）/ faster-whisper |
| numpy | 21.5 MB | 音声の共通表現（16 kHz mono float32） |
| tokenizers | 7.5 MB | faster-whisper |
| huggingface_hub | 4.3 MB | faster-whisper（**取得は無効化している** → ADR-023） |
| av | 3.4 MB | faster-whisper |
| faster_whisper | 1.4 MB | 本体 |
| **合計（増分）** | **約 136 MB** | |

### 判定: **R1 は再燃しない。**

R1 の懸念は「**torch 依存だとインストーラ 1-2 GB**」であり、今回の増分はその 1/10 以下である。
CTranslate2 / ONNX を選んだ判断（[ADR-008](../decisions/ADR-008-provider-abstraction.md)）が
そのまま効いている。

### 配布物サイズ（Step E で配線が通った後）

| 時点 | PyInstaller onedir | **インストーラ**（NSIS） | 備考 |
|---|---|---|---|
| Phase 0 | 26.7 MB | **13.1 MB** | |
| Step C（Provider 実装） | 26.7 MB | — | **増えない**。STT の経路がどこからも import されていない |
| **Step E（配線後）** | **234.8 MB** | **65.7 MB** | 見込み 160 MB を**大きく超えた** |

インストーラが onedir の 1/3.6 で済むのは NSIS が LZMA 圧縮するため。
**判定に使うのはインストーラの 65.7 MB** である（ユーザーがダウンロードするのはこれ）。

見込み（約 160 MB）を外した原因は、**site-packages のサイズだけを足したこと**である。
PyInstaller は依存の**ネイティブ DLL を別途集める**ので、そこが漏れていた。

| 内訳（`_internal/`） | サイズ | 何のため |
|---|---|---|
| **av.libs** | **62.6 MB** | PyAV が同梱する FFmpeg。**Lumi は使っていない**（下記） |
| ctranslate2 | 58.8 MB | STT の推論エンジン |
| onnxruntime | 34.6 MB | Silero VAD（barge-in） |
| numpy.libs | 20.1 MB | OpenBLAS |
| hf_xet | 9.1 MB | huggingface_hub の転送高速化。**取得は無効化している** |
| tokenizers | 7.2 MB | STT |
| その他 | 42 MB | Python 本体 / OpenSSL / SQLite / PortAudio / sqlite-vec / Content Pack |

### 判定: **R1 は再燃しない。** ただし 5 倍になった事実は残す

R1 の閾値は「1-2 GB で配布不能」であり、**インストーラ 65.7 MB はその 1/20 以下**である。
**torch を避けた判断はそのまま効いている。**

比較のため: torch（CUDA 付き）は単体で 2-3 GB、CPU 版でも 200 MB 前後ある。
**CTranslate2 + ONNX Runtime で 93 MB** に収まっているのがこの選択の成果である。

### 削れる見込みがあるもの〔Phase 1 では手を付けない〕

| 対象 | 削減見込み | 障害 |
|---|---|---|
| av.libs + av | **65 MB** | `faster_whisper/__init__.py` が `decode_audio` を無条件 import する。Lumi は音声を **numpy 配列で渡す**ので FFmpeg は実行時に使われないが、**import は通ってしまう** |
| hf_xet | 9 MB | モデルの実行時取得（ADR-023）を自前の HTTP に置き換えれば huggingface_hub ごと外せる |

どちらも「使っていないものを外す」だけで**機能を落とさない**。
**Phase 1 の完了条件には効かないので、やらない。** R1 が再燃したときの余地として記録する。

### ★ 固めた実行体だけで壊れたもの（2026-08-16）

**onnxruntime が読めず、Silero VAD が丸ごと死んだ。** つまり barge-in が動かない。
`uv run pytest` は全て通り、**開発環境では一切再現しない。**

```
ImportError: DLL load failed while importing onnxruntime_pybind11_state:
ダイナミック リンク ライブラリ (DLL) 初期化ルーチンの実行に失敗しました。
```

原因は **PyInstaller がビルド機の PATH から VC++ ランタイムを拾ったこと**。
このマシンでは JDK の同梱物が先に見つかっていた。

| DLL | 拾われた版 | 出所 | System32 |
|---|---|---|---|
| msvcp140.dll | **14.16**（VS2017） | `C:\Program Files\Microsoft\jdk-11.0.16.101-hotspot\bin` | 14.51 |
| vcruntime140.dll | **14.16** | 同上 | 14.51 |

onnxruntime.dll はもっと新しいものを要求するため、DllMain が失敗する。

**対処**: `lumi-core.spec` の `_pin_vcruntime()` が、収集された VC++ ランタイムの出所を
**System32 に固定する**。PATH を直すのではなくビルド定義で固定するのは、
**配布物がビルド機の状態に左右されること自体が問題**だからである。

**この種のバグは実行するまで分からない。** `--self-check` に Silero VAD / faster-whisper /
Content Pack の項目を足したのはそのためで、**CI で配布物を検査できる唯一の手段**である。

```
> lumi-core.exe --self-check
  ✓ sqlite-vec / ✓ FTS5 / ✓ PortAudio / ✓ Silero VAD / ✓ faster-whisper
  ✓ Content Pack / ✓ TLS
```

### モデルは含まない

ランタイム（上記）は同梱するが、**STT のモデル（数百 MB）は配布物に含めない**
（ユーザーの明示的な選択に基づく実行時取得 → [ADR-023](../decisions/ADR-023-llm-runtime-and-model-acquisition.md)）。
Silero VAD（数 MB）は同梱する。

## ★ 実測で見つかった4つ

### 1. 計器が2箇所間違っていた（最初の測定は捨てた）

| 誤り | 何が起きたか |
|---|---|
| `total_ms` が**発話全体**を測っていた | 全文の再生完了までを含み、p50 10 秒と出た。SLO は「**最初の音が出るまで**」 |
| 区間を**境界から境界**で測っていた | 隙間の時間が次の区間に混ざる。`unaccounted_ms` が構造的にゼロになり**警告灯が死ぬ** |

**区間は「その区間自身の仕事」を測る**（明示的な begin / end）に直した。
隙間が `unaccounted_ms` に出るようになって初めて、予備枠の警告灯が意味を持つ。

### 2. ★ モデルが既定で「思考」しており、`think=False` が無視されていた

`OllamaProvider` は `think: True` のときだけフィールドを送っていた。
**ハイブリッド推論モデル（Qwen3.5 等）は既定で思考する**ので、省略すると既定が残る。

| | 最初の**発話可能な**トークンまで |
|---|---|
| 思考あり（既定） | **5578 ms**（thinking 82 チャンク → content） |
| `think: false` を明示 | **272 ms** |

**単独で最大の改善**（-1534 ms）。`ReasoningDelta` を TTS に流さない実装は正しかったが、
**流さないだけでは遅延は消えない。**

### 3. ★ 先読み並列生成が、第1文を遅くしていた

TTS エンジンは1リクエストで**デバイスを飽和させる**。実測（CPU）:

| | |
|---|---|
| 1リクエストの CPU 時間 | **19.3 秒**（実時間 836 ms、**並列度 23.1x**） |
| 4並列の総時間 | 3.28 秒 |
| 逐次の総時間 | 3.35 秒 |

**総時間は変わらず、1本あたりが4倍に伸びるだけ。** 第1文が後続と資源を取り合って遅くなる。
`MAX_PARALLEL` を 1 にして `tts_first_audio_ms` 865 → 573 ms。
→ [audio.md](../architecture/audio.md) §6 を書き換えた

### 4. ✓ `vad_ms` の予算 0.18 秒が、VAD のパラメータと矛盾していた〔2026-08-17 解決〕

予算表は「`min_silence_duration_ms` に律速される」と書いているが、
**そのパラメータの値は 400 ms** である（[audio.md](../architecture/audio.md) §5）。
実測 429 ms は**パラメータどおり**であり、予算の方が間違っている。

**どちらを直すかは未決。**

| 案 | 得るもの | 失うもの |
|---|---|---|
| 予算を 0.43 s に直す | 正直になる | 区間合計が p50 目標を超える |
| `min_silence_duration_ms` を 200 ms に下げる | **-200 ms** | 文中の自然な間で区間が切れる |

**「切れる」は仮定ではない。〔2026-08-17 実測〕**
2文（3.14 秒）の音声を capture → VAD 経路に流したところ、**現行の 400 ms でも既に2区間に分割された**
（1文目 1.25 秒で SPEECH_ENDED、残りが別区間）。STT は1区間目を正しく認識したが、
**Lumi は1文目だけを聞いて返事を始める**ことになる。200 ms に下げれば、これは読点程度の間でも起きる。

**決着〔2026-08-17〕: 予算の側を直した。** パラメータは 400 ms のまま。
`vad_ms` は実装のコストではなく「ユーザーが喋り終わったと判断するまで待つ」という方針の値であり、
**最適化で消えない。** 表には数値を書かず §5 の `min_silence_duration_ms` を参照する
（同じ値を2箇所に別々に書いたことが原因だった）。
→ [../architecture/audio.md](../architecture/audio.md) §7

**帰結**: 区間合計は p50 目標内に収まった（1.27 / 1.50 = 85%）〔2026-08-18〕。
**レイテンシ条件の p95 2.0 秒も満たしている。** ただし、これはレイテンシ条件の達成であり、Phase 1 全体の完了を意味しない。
手動のマイク入力 / barge-in validation、別マシンでのセットアップ検証、ネットワーク断線の実試験が未完了である。→ [../roadmap.md](../roadmap.md)

## ★ 起動直後の1ターン目が 7.5 秒だった〔2026-08-18 実測〕

ユーザー報告「実際の起動時、最初めっちゃ回答に時間かかる」。実機のログ:

```
vad_ms 403 / stt_ms 277 / assemble_ms 0 / llm_first_token_ms 714
llm_first_segment_ms 16 / tts_first_audio_ms 3721 / playback_ms 34
total_ms 7486 / unaccounted_ms 2321
```

**原因は1つではなく、3つの Provider が全部「ロードしたふり」をしていた。**

| 何が冷たかったか | 誰が払っていたか | 実測 |
|---|---|---|
| Ollama の重みが VRAM に無い | `llm_first_token_ms` | **3767 ms**（cold 4239 → warm 472） |
| AivisSpeech の話者モデルが未初期化 | `tts_first_audio_ms` | **3092 ms**（`initialize_speaker` の所要時間そのもの） |
| faster-whisper のモデルが未構築 | **どの区間でもない** → `unaccounted_ms` | **2489 ms**（報告値 2321 とほぼ一致） |

`load()` はどれも「繋がるか」「在るか」しか確認しておらず、**成功を報告してから最初のターンに
請求書を回していた。** 規則にした → [../interfaces/provider.md](../interfaces/provider.md)
「`load()` は接続確認ではない」

### STT だけが計器から消えていた

`stt_ms` は `transcribe()` を測る。**モデルの構築はその外側**なので、2489 ms は
どの区間にも入らず `unaccounted_ms` に化けていた。

**これは `unaccounted_ms` が意図どおり働いた例である。** 「計測していない処理が増えている」と
警告灯が点り、実際にそのとおりだった。ただし**予備枠 130 ms に対して 2321 ms** であり、
警告灯としては振り切れていた。

### ★ 同じバグを2度書いていた — LLM のクライアント使い捨て〔2026-08-18 実測〕

**ターンごとに `httpx.AsyncClient` を作り直していた。** これは改善経過 ④ で TTS 側を直したのと
**同一のバグ**で、LLM 側だけ残っていた。

| | 1ターン目 | 以降（中央値） |
|---|---|---|
| 毎回新規（それまで） | 554 ms | **569 ms** |
| 使い回し（現在） | 644 ms | **421 ms** |

`AsyncClient()` の構築だけで **202 ms**（SSL コンテキスト + プロキシ環境変数の解決）。
**予算 280 ms の区間に、毎ターン 148 ms の固定費を載せていた。**

> **`aivisspeech.py` の docstring には最初からこう書いてあった** — 「リクエストごとに
> クライアントを作ると接続確立を毎文払い、それは `tts_first_audio_ms` に乗る」。
> **警告は書かれていたが、隣のファイルには適用されていなかった。**

### 対策と、その後

| 対策 | 効果 |
|---|---|
| `load()` で実際に重みを載せる（`messages: []`） | 3767 ms を起動時（誰も待っていない）に移した |
| `keep_alive` を明示 | **5分無操作での退避を止めた**（Ollama の既定は5分。デスクトップ常駐はそれより長く黙る） |
| `initialize_speaker`（`skip_reinit`） | 3092 ms を起動時に移した。初期化済みなら **2 ms** |
| STT を起動時にウォーム | 2489 ms を起動時に移した。`unaccounted_ms` が本来の意味に戻る |
| LLM の HTTP クライアントを使い回す | `llm_first_token` **569 → 421 ms**（-148 ms） |

**`llm_first_token` 実測（ウォーム、qwen3.5:9b Q4_K_M / RTX 4070 Ti）**

```
load() = 4277 ms  （起動時）
llm_first_token = [644, 421, 432, 418, 392]  中央値 421 ms
```

1回目の 644 ms は system prompt の KV キャッシュが冷たいため。2回目以降は ~420 ms に落ち着く。

#### 測ったが採らなかったもの

**起動時に system prompt を1トークンだけ通して KV キャッシュを温める**（3試行）:

| | 起動時の追加費用 | 1ターン目 |
|---|---|---|
| `messages: []` のみ | — | 639 ms |
| system prompt も通す | +約 300 ms | 590 ms |

**約 50 ms のために、起動時に本番の推論を1回走らせることになる。** 効果が固定費に見合わず、
「Lumi が起動時に勝手に喋りかけている」ように見える経路を増やす。**採らない。**

### 常駐を解放する

`keep_alive` は Lumi が要求した予約なので、**`unload()` で返す**（`keep_alive: 0`）。
返さないと、Lumi を終了した後も数 GB が確保されたままになる。**それは Lumi のメモリではない。**

**異常終了した場合は Ollama を再起動するまで確保が残る。** これは受け入れる —
代わりに得るのは「昼休みから戻って話しかけても4秒待たない」ことである。

## ★ 1ターン目がまた 4.3 秒だった — 重みを載せても冷たかった〔2026-08-22 実測〕

ユーザー報告「また初回起動時に応答が遅くなってる（2回目以降は正常）」。実機のログ:

```text
vad_ms 401 / stt_ms 1789 / llm_first_token_ms 421 / llm_first_segment_ms 58
tts_first_audio_ms 1584 / playback_ms 26 / total_ms 4282 / unaccounted_ms 3
```

**8月18日の対策は効いている。** `unaccounted_ms` は 3 ms（モデル構築は起動時に移った）、
`llm_first_token_ms` は 421 ms（ウォーム時の中央値そのもの）。残ったのは STT と TTS だけである。

### 「重みが載っている」は「本番レイテンシで返せる」ではなかった

同一マシンで起動シーケンス（TTS 起動 → Ollama preload → STT 構築 → 13 秒待つ → 1ターン目）を
再現して測った。

| | 1ターン目 | 2ターン目以降 | 差 |
|---|---|---|---|
| `stt_ms` | **1486 ms** | 146〜151 ms | **+1.34 s** |
| TTS の合成 | **1579 ms** | 191〜221 ms | **+1.36 s** |

**どちらも「初回の推論そのもの」の費用である。** CUDA のカーネルは遅延ロードされ、cuBLAS は
初回呼び出しで初期化される。CTranslate2 も AivisSpeech のセッションも、重みを載せた時点では
まだ一度も動いていない。

> **8月18日に書いた規則は、はじめから今回の分も含んでいた** —
> 「`load()` を終えた Provider は、**次の呼び出しを本番レイテンシで返せなければならない**」。
> 直したのは「重みを載せる」までで、**規則が要求していたのは「一度動かす」までだった。**

### 対策 — `load()` の最後に一度だけ捨て推論する

| Provider | 何を通すか | 費用（起動時、誰も待っていない） |
|---|---|---|
| STT | 1 秒の無音を `transcribe`。**Whisper は入力を 30 秒にパディングする**ので長さは効かない | 約 300 ms |
| TTS | 短い1文を `synthesize` して**捨てる**（再生経路には何も繋がっていない） | 約 710 ms |

**同じ再現手順での結果**:

| | 対策前 | 対策後 |
|---|---|---|
| 1ターン目の `stt_ms` | 1486 ms | **200 ms** |
| 1ターン目の TTS 合成 | 1579 ms | **415 ms** |

**1ターン目の合計で約 2.4 秒**。`total_ms` 4282 → 約 1900 ms 相当で、p50 目標 1.50 s の
外側ではあるが、2ターン目以降（約 1.15 s）との差は誤差の範囲に入った。

### 暖機の失敗は「壊れている」ではない

捨て推論が失敗しても `load()` は成功させ、警告だけ出す（`stt.warmup_inference_failed` /
`tts.warmup_synthesis_failed`）。**暖機が決めるのは「いつ払うか」であって「払えるか」ではない。**
ここで失敗を致命にすると、一度きりの推論のつまずきで `warm_stt` / `warm_tts` が `failed` を報告し、
boot phase が `blocked` に落ちて**キャラクターが出てこない**（ADR-034）。
話者初期化の失敗を「遅いが壊れてはいない」と扱った 8月18日の判断と同じである。

## 推論スタックの配置〔2026-08-16 実測〕

[ADR-025](../decisions/ADR-025-tts-on-gpu.md) の根拠になった数値。

| | CPU | GPU | VRAM |
|---|---|---|---|
| STT（1.2〜3.0 秒の音声） | 916〜984 ms | **50〜85 ms** | +417 MiB |
| TTS（第1文） | 約 900 ms | **約 420 ms** | +1020 MiB |

**合計 VRAM: LLM 5.5 + TTS 1.0 + STT 0.4 = 6.9 / 12 GB。**

### TTS の合成時間は、CPU では文字数に依存し、GPU ではほぼ一定

| 入力 | CPU | GPU |
|---|---|---|
| 3文字 | 863 ms | 340 ms |
| 5文字 | 859 ms | 348 ms |
| 9文字 | 991 ms | 323 ms |
| 17文字 | 1230 ms | 346 ms |

**CPU は約 800 ms の固定費 + 25 ms/文字。** 前後の無音パディングを 0 にしても減らない
（音声が短くなるだけ）。**第1セグメントを短く切っても CPU の TTS は速くならない。**

GPU では長さにほぼ依存しないので、**遅延が予測可能になる**。

## ★ STT 精度を壊していたのはリサンプラだった〔2026-08-17 実測 → [ADR-026](../decisions/ADR-026-polyphase-resampler.md)〕

「認識精度がメチャクチャ悪い」の原因を、モデルでもデコード設定でもなく
**48 kHz → 16 kHz の変換**に特定した。

### 折り返し（エイリアシング）

8 kHz より上は消えなければならないのに、**ほぼ減衰せずに音声帯域へ移動していた。**

| 入力 | 出力でのピーク | 修正前 | 修正後 |
|---|---|---|---|
| 9 kHz | 7 kHz | −5.6 dB | **−48.0 dB** |
| 10 kHz | 6 kHz | −7.2 dB | **−50.2 dB** |
| 11 kHz | 5 kHz | −9.0 dB | **−51.9 dB** |
| 12 kHz | 4 kHz | −11.3 dB | **−53.4 dB** |
| 18 kHz | 2 kHz | −20.9 dB | **−61.9 dB** |
| 20 kHz | 4 kHz | −16.5 dB | **−65.7 dB** |

**日本語の摩擦音（し / す / つ / しゅ / ち）は 5〜12 kHz にエネルギーの大半がある。**
つまり喋るたびに、全摩擦音の鏡像が子音識別帯域の上に −6 dB で重ねられていた。

### チャンク境界

VAD スレッドは 32 ms ごとに変換を呼ぶ。状態を持たない関数は毎回フィルタを再スタートする。

| | 一括変換との SNR |
|---|---|
| 修正前（純関数を 1536 サンプルずつ） | 22.8 dB |
| 修正後（`StreamingResampler`） | **166.0 dB** |

### 代償と、かかった額

| | 値 |
|---|---|
| 通過域 100 Hz 〜 6 kHz | ±0.00 dB |
| 通過域 7 kHz | −1.15 dB（遷移帯域） |
| DC ゲイン | 1.000 |
| コスト / 32 ms チャンク | **0.024 ms**（VAD 予算 30 ms） |
| 追加した依存 | **無し**（numpy のみ。soxr は LGPL、scipy は 40 MB） |

### 教訓

**この故障は Core が出すどの指標にも現れなかった。** `stt_ms` は正常、`vad_ms` も正常、
オーバーフローもドロップもゼロ。出ていたのは「認識結果が変」だけだった。

**聞けば1秒で分かった。** そのために `LUMI_DEBUG_STT_DUMP=1` を入れた
（`lumi/audio/dump.py` → STT に渡った音声そのものを WAV + 認識結果で書き出す）。

## ★ 残っていた語頭欠落は、プリロール不足だった〔2026-08-17 実測〕

リサンプラ修正後もまだ認識が微妙だったので、**AivisSpeech で日本語を合成し、
48 kHz マイク相当に変換して実パイプライン（リング → VadWorker → STT）に流す**
ベンチを組んで測り直した。正解が既知なので CER が出せる。

### 誤りが全部「語頭の欠落」だった

| 正 | 出（当時の設定） |
|---|---|
| **ちょ**っと聞きたいことがあるんだけど | 聞きたいことがあるんだけど |
| **さっ**きの話の続きをしてもいいかな | の話の続きをしてもいいかな |
| **つく**えの上に置いてある資料を確認して | おいてある資料を確認して |

**落ちた語はすべて無声子音で始まっていた。** 同じ音声をファイル全体で認識させると
語頭は正しく出る（`ちょっと聞きたいことはあるんだけど`）ので、モデルではない。

**Silero の確率は無声子音では上がらない。** 上がるのは後続の母音に入ってからで、
そこから遡って 80 ms のプリロールでは子音が区間の外にある。

### `speech_pad_ms`（24文、faster-whisper small / CUDA int8_float16）

| `speech_pad_ms` | CER |
|---|---|
| 80（当時） | 10.6% |
| 320 | **7.0%** |
| **400（採用）** | **7.0%** |
| 480 | 7.9% |

区間内のセグメント先頭を直接確認しても一致する（80 ms では区間が「ちょっと」の途中から
始まっていた）。**プリロールは既にリングにあるフレームなので、遅延は増えない。**

### `beam_size` は誤差の範囲だった

| | CER | ms/発話 |
|---|---|---|
| `beam_size = 1`（現行） | 3.8 – 7.7% | 88 – 96 |
| `beam_size = 3` | 4.5% | 104 |
| `beam_size = 5` | 3.0 – 8.1% | 110 – 114 |

**走らせるたびに順位が入れ替わる。** ばらつきの主因はハーネスのスレッドタイミングで
区間の切れ方が変わることで、beam 幅の効果はそれに埋もれる。
**`beam_size = 1` のままとする**（約 20 ms 安い）。

### `initial_prompt` は害になる

「以下は、日常会話の音声です。」を与えると CER 10.2% → **16.0%** に悪化した。
**プロンプトの語が出力に漏れる**（`さっきの話` → `日常会話の話`）。使わない。

### 効いた順

| 修正 | CER |
|---|---|
| 修正前（移動平均リサンプラ + `speech_pad_ms = 80`） | — |
| リサンプラを polyphase FIR に（[ADR-026](../decisions/ADR-026-polyphase-resampler.md)） | 10.6% |
| **`speech_pad_ms` 80 → 400** | **7.0%** |

〔未実施〕実際のマイク音声での再測定。合成音声は無声子音がきれいに出るため、
**実マイクではプリロールの効果はもっと大きい可能性がある。**

## ★ 残った誤りは語彙混同で、モデルを替えるしかなかった〔2026-08-17 実測 → [ADR-027](../decisions/ADR-027-stt-model-large-v3-turbo.md)〕

リサンプラとプリロールで**語頭欠落は消えたが、残った誤りの性質が変わっていた**。

> 京都に行ってきたよ → **ちょっと**に言ってきたよ
> 昼ご飯まだ食べてないんだよね → **白ご飯は**食べてないんだよね
> 資料をまとめて送っておくね → 資料をまとめて**おくって**おくね

**これは探索幅やプリロールで消える誤りではない。** モデルの語彙知識の問題である。

### `small` vs `large-v3-turbo`（同一の発話区間 24 文 / RTX 4070 12 GB）

**同じ音声区間を両モデルに通した。** VAD の切り方の差を排除している。

| | `small` | **`large-v3-turbo`** | `large-v3-turbo` (float16) |
|---|---|---|---|
| CER | 7.2% | **3.6%** | 3.6% |
| 誤りのあった文 | 8 / 24 | **3 / 24** | 3 / 24 |
| p50 | 88 ms | **143 ms** | 150 ms |
| p95 | 100 ms | **149 ms** | 155 ms |
| VRAM | 424 MiB | **1024–1243 MiB** | 1980 MiB |
| コールドロード | 0.8 s | 2.4 s | 1.3 s |
| ダウンロード | 484 MB | **1.62 GB** | 同左 |

**`stt_ms` の予算 220 ms に対し p95 149 ms。内側に収まる。**

### `int8_float16` を維持する理由

`float16` と比べて **CER は同一（3.6%）、p50 はむしろ速く（143 対 150 ms）、VRAM は半分**。
重みを float16 で持つ利点が1つも無い。

### 残った3件

再測定すると2件は正しく出た（`おはよう。今日はいい天気だね` / `京都に行ってきたよ`）。
**ばらつきの主因はハーネスのスレッドタイミングで区間の切れ方が変わることである。**
また CER には句読点差（`おはよう。` と `おはよう`）も含まれているので、
**内容の誤り率はこの数字より低い。**

### 実 Provider での確認

pin（SHA-256 × 5ファイル）→ `install_stt_model` → `FasterWhisperProvider` の経路を通した。

```
setup.model.download.verified  files=5 model=large-v3-turbo
stt.loaded  device=cuda provider=faster-whisper:large-v3-turbo
p50 138 ms / max 186 ms / cold load 2.3 s / VRAM ~1243 MiB
```

**保証しないこと**: すべて AivisSpeech の合成音声である。**実マイク・実話者での WER は測っていない。**
話者性・環境雑音・マイク特性はどれもこの数字に入っていない。
